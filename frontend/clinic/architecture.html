Hash
Three separate HMAC-SHA256 hashes generated
Each token is derived independently using a different secret. The clinic-specific salt means even with the database, cross-clinic correlation is impossible.
# hashing.py — runs server-side only # 1. Lost-device recovery (LOOKUP_SECRET isolated separately) lookup_hash = hmac.new( LOOKUP_SECRET.encode(), f"9876543210:0".encode(), hashlib.sha256 ).hexdigest() → a3f8c2d1... # 2. Cross-network identity (user_salt = 32-byte random, permanent) network_token = hmac.new( SECRET_KEY.encode(), f"9876543210:0:{user_salt}".encode(), hashlib.sha256 ).hexdigest() → 7b9e4f2a... # 3. Clinic-scoped identity (clinic_salt = 64-byte random, per clinic) local_token = hmac.new( f"{SECRET_KEY}:{clinic_salt}".encode(), f"9876543210:0".encode(), hashlib.sha256 ).hexdigest() → c1d5a8e3... # Phone deleted from memory payload.phone = "DELETED" phone = "DELETED"

Security Stack

5 independent layers of hardened security

Each layer is independent — a breach of one does not compromise the others.

1
Phone Number Privacy
Patient phone is hashed client→server in HTTP body, immediately passed to HMAC hashing function, then memory-wiped. No column in any table stores a phone number in plaintext.
HMAC-SHA256
2
Clinic Data Isolation
Every clinic has a unique 64-character random clinic_salt. The same patient produces a completely different local_token at each clinic — cross-clinic correlation is mathematically blocked.
Per-clinic salt
3
Password Security
Passwords hashed with PBKDF2-HMAC-SHA256 at 200,000 iterations with a 32-byte cryptographically random salt per password. Constant-time comparison prevents timing attacks. Same standard as 1Password and Django.
PBKDF2 · 200k iter
4
OTP Authentication
OTPs are HMAC-hashed before database storage — the plaintext OTP is never persisted. Verification uses hmac.compare_digest() for constant-time comparison, preventing timing-based side-channel attacks. 10-minute expiry enforced.
HMAC + compare_digest
5
Rate Limiting
Recovery endpoints enforce a maximum of 5 attempts per IP per hour using a sliding-window algorithm. HTTP 429 returned on breach. Protects against brute-force enumeration of patient lookup hashes.
5 req / IP / hour
Future Scope

Next: Zero-Trust End-to-End Encryption

The current architecture prevents server-side re-identification. The next frontier is client-side encryption — so even the server never sees patient medical data in plaintext.

🔏
Client-Side AES-GCM Encryption
Medical records (diagnosis, prescription, vitals) encrypted in the browser using the Web Crypto API with AES-256-GCM before transmission. The server stores only ciphertext — it cannot read patient medical data even with full database access.
Browser: diagnosis = "Hypertension Stage 2"
AES-256-GCM encrypt(key derived from patient_id)
→ sends: a3f9c2d1b8e7... (ciphertext)
Database: stores ciphertext only
Browser: decrypts locally on fetch
Roadmap v2
🗝️
Patient-Controlled Key Derivation
Encryption keys derived from a patient's ABHA ID + a PIN they choose. The doctor sees decrypted records only when the patient presents their QR code — consent-gated by cryptographic key sharing, not by policy.
Patient presents QR
→ ephemeral_key = HKDF(ABHA_ID + PIN)
→ Doctor browser decrypts record
→ key never leaves browser
